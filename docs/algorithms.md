# Алгоритмы приоритизации

Код: `packages/core/src/scoring/`. Все функции чистые и детерминированные: одинаковый вход даёт одинаковый результат, кроме `meta.computedAt`. Внутри расчёты идут без округления. В ответе tools баллы округляются до 4 знаков, проценты до 2.

## 1. Ранжирование и tie-break

Сортировка по трём ключам:

1. балл по убыванию;
2. «размер» по возрастанию: `effort` для RICE, `jobSize` для WSJF, `effort` или `jobSize` для CUSTOM, если поле есть среди весов;
3. `id` по возрастанию (сравнение строк по кодам символов).

Элементы без нужных полей получают `rank: null` и идут после ранжированных в порядке входа. При `strict: true` (по умолчанию) это ошибка `VALIDATION_ERROR` со списком всех недостающих полей.

## 2. Формулы

| Метод  | Формула                                                                                                                                        | Шкалы                                                          |
| ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| RICE   | `reach × impact × confidence / effort`                                                                                                         | impact ∈ {0.25, 0.5, 1, 2, 3}; confidence ∈ [0, 1]; effort > 0 |
| WSJF   | `(businessValue + timeCriticality + riskReductionOpportunity) / jobSize`                                                                       | модифицированный Фибоначчи {1, 2, 3, 5, 8, 13, 20}             |
| CUSTOM | `Σ wᵢ · normᵢ`, где `normᵢ = (x − min)/(max − min)` по набору; для полей из `invert` берётся `1 − norm`; если все значения равны, `norm = 0.5` | веса — любые числа                                             |

`calculate_wsjf` с `normalize: true` делит каждый компонент на его минимум в наборе: самый маленький элемент становится 1, как в относительной оценке SAFe.

Предупреждения:

- `LOW_CONFIDENCE` — `confidence < 0.5`.
- `EXCLUDED_INCOMPLETE` — элементы без полей при `strict: false`.
- `FIB_SCALE_SATURATED` — больше 50% элементов имеют одно значение компонента WSJF.

## 3. Сравнение методов (`compare_initiatives`)

- Сравниваются только элементы, которые могут оценить **все** выбранные методы. Остальные попадают в `excluded` и в warning.
- `kendallTau` считается попарно (tau-a; ранги уникальны, поэтому он равен tau-b). В `agreement` лежит среднее по парам.
- `topNOverlap = |top-N(A) ∩ top-N(B)| / N`.
- **Расхождение** — элемент, у которого разброс рангов между методами `≥ max(3, ⌈0.2 · n⌉)`. Список отсортирован по убыванию разброса.
- **Drivers** — машинные коды `HIGH_<FIELD>` и `LOW_<FIELD>`.
  - `HIGH_<FIELD>`: значение ≥ 80-го перцентиля и строго выше медианы набора.
  - `LOW_<FIELD>`: значение ≤ 20-го перцентиля и строго ниже медианы.
  - Условие «строго от медианы» нужно, чтобы на поле, где у большинства одно значение, помечались только выбросы.
- `consensusTop` — элементы, которые входят в top-N у всех методов, в порядке первого метода.

## 4. Сценарии ёмкости (`simulate_capacity`)

Жадный алгоритм. Ранжирование считается один раз (методом `rankBy`), сценарии его не меняют.

1. **Проверки.** У каждого элемента должен быть `effort`. Граф `dependsOn` не должен содержать циклов (ошибка показывает путь цикла) и ссылок на неизвестные id. `forceExclude` не может исключать `mandatory`- и `forceInclude`-элементы.
2. **Пулы ёмкости.** Элемент тратит ёмкость своей команды (`team`). Если записи для команды нет — тратит общий пул `"*"`. Если нет и его — элемент откладывается с причиной `CAPACITY` и warning `NO_CAPACITY_FOR_TEAM`.
3. **Множители сценария.** Ёмкость умножается на `capacityMultiplier`, effort — на `effortMultiplier`.
4. **Закреплённые элементы.** `mandatory` и `forceInclude` берутся первыми, в порядке ранга, вместе с транзитивными зависимостями, **даже если ёмкость превышена**. Тогда сценарий получает `overCommitted: true`.
5. **Остальные элементы** перебираются по рангу.
   - Элемент из `forceExclude` → `FORCED_OUT`.
   - Если в «пакете» элемента (он сам плюс ещё не взятые зависимости) есть принудительно исключённый элемент или элемент, отложенный по `DEPENDENCY`/`FORCED_OUT`, → `DEPENDENCY` с `blockedBy`.
   - Иначе весь пакет берётся, если помещается во все задействованные пулы. Зависимости получают `via: "DEPENDENCY"`. Если пакет не помещается → `CAPACITY`, а в `blockedBy` перечислены зависимости из пакета.
6. **Итоги.** `utilization` по каждому пулу: `pct = used / capacity · 100`, `null` при нулевой ёмкости. `totalScoreIncluded` — сумма баллов взятых элементов (`null` для `INPUT_ORDER`). `diffVsFirst` — added/removed относительно первого сценария.

Жадный выбор объясним, но не оптимален. Поэтому сокращение ёмкости может впустить мелкий элемент, который в базовом сценарии не помещался. Это видно в `diffVsFirst`. Оптимизатор (knapsack) — кандидат в v0.3 как отдельный режим.

## 5. Объяснение рейтинга (`explain_ranking`)

**Вклад компонентов.** Для каждого компонента считается `vsMedian = ln(значение / медиана набора)`. Для компонентов «меньше — лучше» (`effort`, `jobSize`) знак инвертируется. Положительное значение тянет балл вверх. `logShare = |vsMedian| / Σ|vsMedian|` — доля компонента в отличии элемента от медианного. Для WSJF компоненты — `costOfDelay` и `jobSize`, а `costOfDelayBreakdown` показывает доли трёх слагаемых в CoD.

Такая декомпозиция не зависит от единиц измерения. Наивное разложение `ln(reach) + ln(impact) + …` всегда «отдавало бы» вклад reach, потому что reach измеряется тысячами.

**Чувствительность.** Ищется минимальное изменение **одного** компонента, после которого элемент обгоняет соседа выше (`toOvertake`) или сосед ниже обгоняет его (`toBeOvertaken`).

- Непрерывные компоненты (reach, confidence, effort): значение безубыточности считается аналитически и округляется до 4 знаков **в сторону от ничьей**.
- Дискретные компоненты (impact, все поля WSJF): перебираются значения шкалы.
- Каждый найденный вариант проверяется пересчётом ранга. Property-тест подтверждает, что напечатанное значение действительно меняет ранг.
- `null` означает, что одним компонентом этого не добиться: confidence упирается в 1, шкала Фибоначчи кончилась, или балл равен 0.

**Флаги.**

- `LOW_CONFIDENCE` — `confidence < 0.5`, только RICE.
- `HIGH_EFFORT_OUTLIER` — размер больше Q3 + 1.5·IQR.
- `SINGLE_COMPONENT_DOMINATES` — `logShare > 0.6` при хотя бы двух ненулевых компонентах.
- `NEAR_TIE` — разница с соседом меньше 5%.

## 6. Отличия от спецификации v0.1

| Место                      | Спецификация                                       | Реализация                                   | Причина                                                             |
| -------------------------- | -------------------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------- |
| §5.5 зависимости           | элемент берётся, только если зависимости уже взяты | зависимости подтягиваются пакетом            | иначе ценный элемент с низкоранговым enabler всегда откладывался бы |
| §5.6 `contributions`       | доля `log(score)`                                  | `vsMedian` + `logShare` относительно медианы | независимость от единиц (см. §5)                                    |

| §5.1 источники             | `inline`, `file`                                   | плюс `demo` (встроенный датасет)             | демо в любом клиенте без настройки путей                            |
| §5.4 `agreement`           | одно значение                                      | плюс `pairs` для 3 методов                   | при 3 методах среднее скрывает, какая пара расходится               |
